## 1. الدستور الهندسي لمسارات الـ API والأمان (API Architecture & Security)

### 1.1 معايير الروابط ونظام التشفير
- جميع نقاط النهاية (Endpoints) تبدأ بالبادئة:  
  `/api/v1/`
- تُمرر المصادقة إجبارياً عبر ترويسة الطلب:  
  `Authorization: Bearer <JWT_TOKEN>`
- **الأمان المطلق لعزل الشركات:**  
  يتم استخراج `tenant_id` برمجياً من داخل التوكن المشفر (JWT Claims) في طبقة الحماية (Middleware). **ممنوع منعاً باتاً** قبول `tenant_id` كـ Parameter في جسم الطلب أو الـ URL لمنع أي تلاعب أو انتحال بين المستأجرين.

### 1.2 بنية الاستجابة الموحدة (Standard JSON Response)
تلتزم جميع مسارات المنظومة بنمط استجابة موحد دون استثناء:

#### في حال النجاح (HTTP 200 / 201):
```json
{
  "success": true,
  "status_code": 200,
  "message": "تم تأكيد وتسجيل الطلب بنجاح",
  "data": { ... }
}
```

#### في حال الخطأ (HTTP 400 / 401 / 403 / 422):
```json
{
  "success": false,
  "status_code": 422,
  "error_code": "INSUFFICIENT_FEFO_STOCK",
  "message": "الكمية المطلوبة غير متوفرة في التشغيلات السارية بالمخزن",
  "details": {
    "product_id": "9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d",
    "requested_qty": 10,
    "available_qty": 6
  }
}
```

## 3. المنطق البرمجي لإدارة سلسلة التوريد والمخزون بنظام (FEFO Logic)

### 3.1 الخوارزمية البرمجية لحجز وصرف المستحضرات:
عند استدعاء مسار إنشاء أو تجميع الطلب:
```python
# خوارزمية السحب الذكي بنظام FEFO
def allocate_fefo_batches(tenant_id, product_id, requested_qty):
    # 1. جلب التشغيلات المتاحة مرتبة بالأقرب انتهاءً أولاً بشرط عدم انتهاء الصلاحية
    batches = db.query(InventoryBatch).filter(
        InventoryBatch.tenant_id == tenant_id,
        InventoryBatch.product_id == product_id,
        InventoryBatch.expiry_date > date.today(),
        InventoryBatch.quantity_available > 0
    ).order_by(InventoryBatch.expiry_date.asc()).all()

    total_allocated = 0
    allocations = []

    for batch in batches:
        needed = requested_qty - total_allocated
        if needed <= 0:
            break
            
        take_qty = min(batch.quantity_available, needed)
        
        # حجز الكمية لمنع بيعها لعميل آخر
        batch.quantity_available -= take_qty
        batch.quantity_reserved += take_qty
        
        allocations.append({
            "batch_id": batch.id,
            "batch_number": batch.batch_number,
            "expiry_date": batch.expiry_date,
            "allocated_qty": take_qty
        })
        total_allocated += take_qty

    if total_allocated < requested_qty:
        raise InsufficientStockException("عجز في المخزون المتاح للصنف")
        
    return allocations
```

### 3.2 تثبيت الخصم الفعلي عند التسليم:
- عند ضغط السائق زر **"تأكيد التسليم بالصورة والتوقيع"** في الشاشة `WH-04`:
  1. يتم خصم `quantity_reserved` نهائياً من رصيد التشغيلة.
  2. يتم توليد حركة مخزنية رسمية بنوع `STOCK_OUT_DELIVERY` في كارت حركة الصنف.
  3. يتم تحديث حالة الطلب فوراً إلى `delivered`.

## 4. محرك العمولات الثلاثي واستردادها التلقائي (Rep Commission & Clawback Engine)

### 4.1 المعادلة المحاسبية للمستحقات الشهرية:
تحسب مستحقات المندوب آلياً في نهاية الشهر كالتالي:
$$\text{صافي الراتب} = \text{الراتب الأساسي الثابت} + \text{عمولة المبيعات المُسلمة} + \text{عمولة التحصيلات النقدية} - \text{استردادات المرتجعات (Clawback)}$$

حيث:
- **عمولة المبيعات:** تُستحق فقط على الطلبات بحالة `delivered` (تم تسليمها للعميل فعلياً). الطلبات الملغاة أو قيد الشحن لا تحسب عليها عمولة.
- **عمولة التحصيل:** تُستحق فور تسجيل سند القبض `payments` ومطابقته نقدياً في المستودع بنهاية اليوم.

### 4.2 آلية الاسترداد التلقائي للعمولة (Automated Commission Clawback):
- في حال قام صالون بإرجاع بضاعة سبق احتساب عمولة بيع عليها للمندوب:
  1. يقوم النظام بحساب العمولة التي صُرفت سابقاً على الأصناف المرتجعة:
     $$\text{Clawback Amount} = \text{قيمة المرتجع} \times \text{نسبة عمولة المندوب الأصلية}$$
  2. يُنشئ النظام قيد استرداد عمولة مرتبط برقم حركة الإرجاع `return_id`.
  3. يُخصم المبلغ تلقائياً من رصيد عمولات المندوب في الدورة الشهرية الحالية مع إظهار تفاصيل ذلك في تقرير عمولته لمنع أي شكوى أو التباس.
